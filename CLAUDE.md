# CLAUDE.md

This file guides Claude Code when working in this repository.

## Project Summary

Backend core for a **medical appointment scheduling system**, consumed primarily by a **real-time Voice AI Agent** through function calling over a REST API. The agent identifies callers by phone number, discovers specialties and doctors, checks availability, and books, lists, or cancels appointments.

Because the main client is a voice agent, responses must be **fast, predictable, and machine-friendly**: stable JSON shapes, explicit error codes, and no ambiguity in dates and times.

## Tech Stack

- **Language / Framework:** Python 3.12 + FastAPI
- **Database:** PostgreSQL
- **ORM:** SQLAlchemy 2.0 (async, typed `Mapped[]` models) with the `asyncpg` driver
- **Migrations:** Alembic
- **Validation / Schemas:** Pydantic v2
- **Settings:** `pydantic-settings`
- **Phone numbers:** `phonenumbers` (E.164 normalization)
- **Dates:** stdlib `datetime` + `zoneinfo`; everything stored in UTC
- **Package manager:** `uv`
- **Lint / Format / Types:** Ruff (lint + format) and mypy in strict mode
- **Testing:** pytest + pytest-asyncio + `httpx.AsyncClient`, against a real PostgreSQL test database

## Architecture (Clean Architecture)

Dependencies point inward only: **API (routers) → Use Cases → Domain ← Infrastructure**. The domain layer must never import FastAPI, SQLAlchemy, or Pydantic.

```
app/
├── main.py                    # app factory, router registration, exception handlers
├── core/
│   ├── config.py              # Settings (pydantic-settings)
│   ├── security.py            # X-API-Key dependency
│   ├── errors.py              # domain error -> HTTP mapping
│   └── clock.py               # Clock protocol + system implementation
├── domain/
│   ├── entities/              # Patient, Doctor, Appointment (dataclasses)
│   ├── value_objects/         # Phone, TimeSlot
│   ├── errors.py              # SlotUnavailableError, BookingNoticeError, ...
│   └── repositories.py        # repository Protocols (interfaces)
├── use_cases/
│   ├── patients/              # lookup_patient_by_phone.py, register_patient.py
│   ├── doctors/               # list_specialties.py, list_doctors.py
│   └── appointments/          # list_available_slots.py, schedule_appointment.py, cancel_appointment.py, ...
├── infrastructure/
│   ├── db/
│   │   ├── session.py         # async engine + session factory
│   │   └── models.py          # SQLAlchemy ORM models
│   └── repositories/          # SqlAlchemyPatientRepository, ...
└── api/
    ├── deps.py                # dependency wiring (session, repos, use cases, clock)
    └── v1/
        ├── routers/           # patients.py, doctors.py, specialties.py, appointments.py
        └── schemas/           # Pydantic request/response models
alembic/
scripts/
└── seed.py
tests/
├── unit/
└── e2e/
```

### Layer rules

- **Routers:** receive validated Pydantic models, call exactly one use case, return a response schema. No business logic and no direct database access.
- **Use cases:** one class per workflow with a single `async def execute(...)` method. Depend on repository `Protocol`s and a `Clock`, injected through the constructor. Wired up in `api/deps.py` via `Depends`.
- **Domain:** plain dataclasses, value objects, domain errors, and pure business rules. Must be unit-testable without a database or event loop where possible.
- **Infrastructure:** SQLAlchemy models and repository implementations, including mapping ORM models to domain entities. ORM models never leak past this layer.
- **Pydantic schemas** belong to the API layer only; do not use them as domain entities.

## Data Model

| Table | Key fields | Notes |
|---|---|---|
| `specialties` | `id` (UUID), `name` | e.g. "Cardiology" |
| `doctors` | `id`, `name`, `email` (unique), `crm` (unique), `specialty_id` (FK) | CRM = Brazilian medical license registry |
| `patients` | `id`, `name`, `email` (unique), `phone` (unique), `birth_date` (Date) | Phone is the primary lookup key |
| `doctor_schedules` | `id`, `doctor_id` (FK), `day_of_week` (0–6, 0 = Sunday), `start_time`, `end_time` | Working-hour templates, in clinic local time. Several non-overlapping windows per doctor and weekday are allowed (e.g. lunch break) |
| `appointments` | `id`, `doctor_id` (FK), `patient_id` (FK), `date_time` (timestamptz, UTC), `duration_minutes`, `status` | Status enum: `PENDING`, `CONFIRMED`, `CANCELLED`, `COMPLETED`. New bookings are created as `CONFIRMED`. `duration_minutes` is copied from `SLOT_DURATION_MINUTES` at booking time |

Use `snake_case` for table and column names. JSON field names in the API stay `camelCase` to match the contract (see below).

**Watch out:** Python's `datetime.weekday()` returns 0 = Monday, but `day_of_week` uses 0 = Sunday. Convert with `(d.weekday() + 1) % 7` in a single helper in `core/clock.py` or the domain, and never inline it.

### Double-booking constraint

Add a **partial unique index** so a cancelled appointment does not block the slot. Declare it on the model:

```python
__table_args__ = (
    Index(
        "appointment_doctor_datetime_active_uq",
        "doctor_id",
        "date_time",
        unique=True,
        postgresql_where=text("status IN ('PENDING', 'CONFIRMED')"),
    ),
)
```

Check that Alembic's autogenerated migration includes the `postgresql_where` clause. Do not remove or weaken this index.

## Business Rules

1. **Time slot conflict validation.** Check for an existing active appointment before inserting, *and* rely on the unique index as the final guard against races. Catch `sqlalchemy.exc.IntegrityError` for that index name and convert it into `SlotUnavailableError` → HTTP 409.
2. **Scheduling window.** Reject bookings in the past or with less than the minimum notice (default **2 hours**, configurable via `MIN_BOOKING_NOTICE_MINUTES`). Reject bookings further out than `MAX_BOOKING_ADVANCE_DAYS` (default **90**) with `BEYOND_BOOKING_HORIZON`.
3. **Template-based availability.** `dateTime` must equal the start of a slot generated from the doctor's `doctor_schedules` windows for that day of week. Anything else (misaligned time, slot that doesn't fit a window, day with no schedule) is `INVALID_SLOT`.
4. **Phone-first identification.** Patients are identified by caller phone. Normalize every phone to **E.164** (e.g. `+5511999998888`) with `phonenumbers` before storing or querying. Any valid E.164 number is accepted; `BR` is only the default region when the input has no `+`.
5. **Patient limits.** A patient may not hold overlapping active appointments, even with different doctors (`PATIENT_TIME_CONFLICT`), and may hold at most `MAX_ACTIVE_APPOINTMENTS_PER_PATIENT` (default **5**) active future appointments (`BOOKING_LIMIT_REACHED`).
6. **Retry safety.** If the active appointment at the requested doctor and time already belongs to the same patient, booking returns that appointment with `200` instead of `409`. A different patient still gets `SLOT_UNAVAILABLE`.
7. **Cancellation.** The request carries `patientId`; a mismatch returns `APPOINTMENT_NOT_FOUND`. Future appointments can be cancelled at any time. Past appointments return `APPOINTMENT_IN_PAST`.

Out of scope for v1: holidays, doctor time off, rescheduling. See `CONTEXT.md` for the full glossary and decisions.

### Slot generation

- Default slot duration: **30 minutes** (configurable via `SLOT_DURATION_MINUTES`).
- Available slots = schedule windows for that weekday, split into slots, minus any slot overlapping an active appointment's interval (`date_time` to `date_time + duration_minutes`, `PENDING`/`CONFIRMED`), minus slots that violate the minimum-notice rule.
- A doctor with no schedule that day, a past date, or a date beyond the booking horizon yields `200` with `availableSlots: []`. An unknown doctor is `404 DOCTOR_NOT_FOUND`.
- Slots are returned as `HH:MM` strings in **clinic local time**.

### Time zones

- Clinic timezone defaults to `America/Sao_Paulo` (`CLINIC_TIMEZONE` env var), loaded with `zoneinfo.ZoneInfo`.
- `doctor_schedules` times and `available-slots` output are in clinic local time.
- `appointments.date_time` is always stored and accepted as UTC ISO 8601 (`2026-10-15T14:00:00Z`). Reject naive datetimes in request schemas.
- Never call `datetime.now()` or `datetime.utcnow()` in use cases; inject a `Clock` so tests can control "now". Always work with timezone-aware datetimes.

## REST API Contract

- **Base URL:** `/v1` (routers mounted with `prefix="/v1"`)
- **Auth:** every route requires header `X-API-Key`, enforced by a dependency applied at the router level and compared to `AI_AGENT_API_KEY` with `secrets.compare_digest`.
- **JSON casing:** request and response bodies use camelCase (`patientId`, `birthDate`, `availableSlots`). Use a shared Pydantic base model with `alias_generator=to_camel` and `populate_by_name=True`, and return responses with `by_alias=True` (FastAPI's default for `response_model`).

| Method | Path | Purpose |
|---|---|---|
| GET | `/patients/lookup?phone=` | Find patient by phone → `{ exists, patient? }` (200 for any well-formed phone; unparseable phone is `400 INVALID_PHONE`) |
| POST | `/patients` | Register patient (`name`, `phone`, `email`, `birthDate`) |
| GET | `/specialties` | List specialties |
| GET | `/doctors?specialtyId=` | List doctors, optionally filtered by specialty |
| GET | `/doctors/{doctorId}/available-slots?date=YYYY-MM-DD` | `{ doctorId, date, availableSlots: ["09:00", ...] }` |
| POST | `/appointments` | Book (`patientId`, `doctorId`, `dateTime`). `201` when created, `200` when the same patient retries an existing booking |
| GET | `/patients/{patientId}/appointments?status=` | List a patient's appointments. Default: upcoming `PENDING`/`CONFIRMED`, ascending. An explicit `status` returns all matches, past included. Each item has `doctor: { id, name, specialty }`. Max 50, no pagination |
| PATCH | `/appointments/{appointmentId}/cancel` | Cancel an appointment (body: `patientId`) |

Type path params as `uuid.UUID` so FastAPI validates them.

### Response and error conventions

- Lookup of an unknown but well-formed phone returns `200` with `{ "exists": false }`, not `404`; the agent uses this to decide whether to register. An unparseable phone is `400 INVALID_PHONE`, so garbage transcriptions never lead to registration.
- Error body shape (produced by exception handlers in `core/errors.py`):
  ```json
  { "statusCode": 409, "error": "SLOT_UNAVAILABLE", "message": "The selected time slot is no longer available.", "requestId": "..." }
  ```
- `X-Request-ID` is accepted if present (short validated string), otherwise generated as a UUID. It is echoed in the response header and in the error body's `requestId`.
- Override FastAPI's default `RequestValidationError` handler so validation errors use the same shape (`error: "VALIDATION_ERROR"`).
- `error` is a stable, UPPER_SNAKE_CASE code the agent can branch on. `message` is short and suitable to be read aloud.
- Status codes: `400` validation, `401` missing/invalid API key, `404` resource not found, `409` slot taken, patient time conflict, or duplicate phone/email, `422` business-rule violation (past date, insufficient notice, invalid slot, beyond horizon, booking limit, cancelling an already cancelled/completed or past appointment), `500` unexpected failure (`INTERNAL_ERROR`, same body shape, never includes exception text).
- Error codes:

  | Status | Codes |
  |---|---|
  | 400 | `VALIDATION_ERROR`, `INVALID_PHONE` |
  | 401 | `UNAUTHORIZED` |
  | 404 | `PATIENT_NOT_FOUND`, `DOCTOR_NOT_FOUND`, `APPOINTMENT_NOT_FOUND` |
  | 409 | `SLOT_UNAVAILABLE`, `PATIENT_TIME_CONFLICT`, `PHONE_ALREADY_REGISTERED`, `EMAIL_ALREADY_REGISTERED` |
  | 422 | `INVALID_SLOT`, `BOOKING_NOTICE_TOO_SHORT`, `BOOKING_IN_PAST`, `BEYOND_BOOKING_HORIZON`, `BOOKING_LIMIT_REACHED`, `APPOINTMENT_IN_PAST`, `APPOINTMENT_NOT_CANCELLABLE` |
  | 500 | `INTERNAL_ERROR` |

  Registration validation (malformed phone, future or >120-year `birthDate`, blank name) is `VALIDATION_ERROR`. If phone and email both clash, report the phone first.
- Domain errors are plain exception classes in the domain layer; only the API layer maps them to HTTP.

## Coding Conventions

- Full type hints everywhere; `mypy --strict` must pass. No `Any` without a justifying comment.
- Async all the way: async routes, async repositories, `AsyncSession`. Never call blocking I/O inside a route.
- One `AsyncSession` per request, provided by a dependency; the use case or a unit-of-work commits, never the repository.
- Modules and functions in `snake_case`, classes in `PascalCase`.
- Prefer adding a new use case over growing an existing one.
- Do not log full patient data (name, phone, email, birth date). This is health data covered by LGPD; mask phones in logs (e.g. `+55119****8888`).
- Logs are structured JSON: request ID, method, route template (never the raw URL, since `?phone=` is in the query string), status, error code, latency. Never log request or response bodies. UUIDs may be logged in full.

## Testing Expectations

- **Unit tests** for every use case and domain rule, using in-memory repository fakes and a fixed `Clock`.
- **E2E tests** with `httpx.AsyncClient` (ASGI transport) must cover at least: phone lookup (found / not found), registration with duplicate phone, slot listing respecting schedules and existing bookings, booking success, booking conflict (409), booking inside the notice window (422), and cancellation freeing the slot.
- Include a concurrency test that fires two simultaneous bookings for the same slot (`asyncio.gather`) and asserts exactly one succeeds.
- Also cover: same-patient booking retry (200), patient time conflict, booking limit, `INVALID_SLOT`, cancel with the wrong `patientId` (404), and `INVALID_PHONE` on lookup.
- Each test runs inside a transaction that is rolled back, or against a freshly migrated database. E2E tests build their own data with factories and never rely on the seed. `scripts/seed.py` is deterministic and idempotent, for local development and demos only.

## Things to Avoid

- Do not put business logic in routers or repositories.
- Do not rely solely on the pre-insert check for conflicts; the database index is the source of truth.
- Do not use naive datetimes, and do not return or accept local-time timestamps for `dateTime`.
- Do not use Pydantic schemas or ORM models as domain entities.
- Do not change the response shapes above without updating this file; the voice agent's function definitions depend on them.
